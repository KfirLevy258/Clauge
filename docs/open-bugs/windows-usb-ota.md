# OPEN: a USB firmware update that never reaches the ROM loader

One customer on Windows, app 1.3.2, board on 1.2.5. They tap Install and it
fails, every time:

```
[bridge] ota: closing port to flash 1.3.2
[bridge] ota: FAILED: Could not check the chip; not flashing
```

Unresolved as of 2026-09-08. This file records what has been measured, so the
next person does not re-derive it.

## It is not the eFuse probe

That sentence comes from `flash_encrypted_chip()` returning None, which is why
this looked like a probe bug for a day. It is not one. `write_flash` goes
through the same `esptool` `connect()`, so removing, retrying or skipping the
probe only moves the failure one line down with different wording. The probe
is simply the first thing in the update that needs the ROM download loader.

## What the customer's log proves

- **The port opened.** From the log's own epoch anchors: `ota_flash` arrives,
  `flash_image` sleeps its deliberate 4 s and closes the port, and the
  reconnect's `time` message lands 28 s later. Minus the 1.5 s reconnect probe
  (`PROBE_S`), the eFuse probe ran for about **26 s** -- esptool's seven
  connect attempts spent in full.
- **The reset line works.** After each failure the board sends
  `{"t":"hello",...,"reset":"0x8"}` and replays the logo. `0x8` is Zephyr's
  `RESET_POR`, which `hwinfo_esp32.c` maps from `ESP_RST_POWERON` -- what
  pulling EN low produces. A firmware `sys_reboot()` would report `0x2`, and
  every deliberate reboot in `main.c` calls `ui_boot_mark_intentional_reboot()`
  first, which would have skipped the splash. It did not.

So DTR/RTS reach the board and reset it, and the chip comes back up running
the **application** instead of the ROM download loader.

## Why that is possible at all

This board's auto-reset circuit is cross-coupled (see the comment in
`claude_usage_bridge.py`, "A PLAIN open"): EN is low only while RTS is
asserted **and** DTR is not; IO0 is low only while DTR is asserted **and** RTS
is not. The two can never be low at the same time. Entering download mode
means crossing from (DTR=0,RTS=1) to (DTR=1,RTS=0), and both intermediate
states -- (1,1) and (0,0) -- release EN with IO0 still high.

esptool's `ClassicReset` sets the lines one at a time:

```python
_setDTR(True)    # releases EN here, IO0 still high
_setRTS(False)   # IO0 low -- one USB control transfer later
```

It works only because EN's RC rise gives the chip a few milliseconds before it
samples the strapping pins. `UnixTightReset` has no such race: it sets both
lines in a single `TIOCMSET` ioctl. And `_construct_reset_strategy_sequence`
in `esptool/loader.py` tries the atomic one **first on macOS and Linux, and
never on Windows** -- Windows only ever gets `ClassicReset`.

## What has been measured, and passes

Run 2026-09-08 on a Windows desk (installed frozen binary, its own board) and
on a Mac with the sequential sequence forced via `ESPTOOL_CFGFILE`:

| case | result |
|---|---|
| Mac, `ClassicReset` forced | 3/3 pass, ~1 s |
| Windows, cold probe | 3/3 pass, ~1 s |
| Windows, faithful handover (open port, `ota_begin`, sleep 4, close, probe on the next line) | **13/13 pass, ~1 s, first attempt** |
| Windows, port deliberately held | **0.2 s**, `PermissionError(13, 'Access is denied.')` |

Two conclusions follow, and both are measurements rather than inferences:

- **Port contention is not the cause.** A held port fails in 0.2 s with an
  explicit message; the customer burns 26 s.
- **The handover is not the trigger.** Reproduced faithfully thirteen times,
  passing on the first connect attempt every time.

The gap is not a timing margin. One second against a full seven-attempt
exhaustion is qualitative; a slightly slower machine does not do that.

## What is left

DTR and RTS are generated by the CH340 **on the board** -- USB carries
neither -- so a bad cable cannot affect the reset circuit, only data. The
customer's log proves RTS works. That isolates the fault to the **DTR -> IO0
path**: either their CH340 driver does not drive DTR the way a working one
does, or that half of the circuit is broken on their unit.

Their board has entered the ROM loader before: `docs/plans/STATE.md` records it
burned from a Mac on 2026-09-04, twice, including after a full `erase_flash`.
`tools/burn.sh` refuses fused chips, so it is not encrypted either.

**What would close it:** the probe's own error text from that machine. "Wrong
boot mode detected" confirms the chip resets and boots the app. "No serial
data received" means this whole chain is wrong. As of the commit that adds it,
the daemon logs that line instead of discarding it.

Failing that, holding the board's BOOT button while the update starts pulls
IO0 low mechanically -- both the test and, if the theory holds, the workaround.

## If it turns out to be general

The robust fix needs firmware: the ESP32 has a `FORCE_DOWNLOAD_BOOT` bit in
`RTC_CNTL_OPTION1_REG`. Setting it and rebooting lands the chip in the ROM
loader with no DTR/RTS involved, after which esptool runs `--before no_reset`.
That removes the race on every platform -- but it cannot rescue a unit already
stuck on firmware that does not have it, which is exactly this customer's
situation. A BOOT-button fallback in the app is what reaches those.

No custom reset sequence helps: both intermediate states release EN with IO0
high, and `CustomReset`'s atomic `U` command is Unix-only.
